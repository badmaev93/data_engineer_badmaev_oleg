# Data Engineer — Тестовое задание

## Быстрый старт

```bash
docker-compose up --build
```

> **Примечание для Linux:** Чтобы контейнеры Airflow гарантированно имели права на запись в смонтированные тома `logs` и `output`, перед запуском можно выполнить:
> ```bash
> mkdir -p logs output && chmod 777 logs output
> ```
> В `docker-compose.yml` также задан `user: "${AIRFLOW_UID:-50000}:0"` для корректной работы с правами хоста.

После запуска:
- **Airflow UI**: [http://localhost:8080](http://localhost:8080) (логин `admin` / пароль `admin`)
- **PostgreSQL**: `localhost:5433`, пользователь `forum`, пароль `forum`, база `fp`

### Порядок работы

1. Открыть Airflow UI → DAGs
2. Запустить **`forum_data_generation`** (Trigger DAG) — генерация данных за октябрь 2026
3. Дождаться завершения (~1-2 мин)
4. Запустить **`forum_log_aggregation`** вручную с параметрами:
   - `date_from`: `2026-10-01`
   - `date_to`: `2026-10-31`
   (или без параметров — тогда DAG обработает данные за `logical_date` в режиме `@daily`)
5. Результат — CSV-файл в директории `./output/`

## Обоснование партиционирования (п. 1.4)

**Стратегия:** `PARTITION BY RANGE (created_at)` с помесячными партициями.

### Почему RANGE по времени?

1. **Append-only характер данных.** Логи пишутся только в текущий месяц — INSERT попадает ровно в одну партицию, что устраняет contention между партициями.

2. **Эффективность запросов по дате и Partition Pruning.** Подавляющее большинство аналитических запросов фильтрует по временному диапазону. В пайплайнах запросы строятся без функций над индексируемой колонкой:
   ```sql
   WHERE created_at >= %s::timestamptz
     AND created_at < (%s::date + INTERVAL '1 day')::timestamptz
   ```
   Сравнение чистого поля `created_at` (без кастов вида `created_at::date`) позволяет планировщику PostgreSQL применять **Partition Pruning** (мгновенно отсекать нерелевантные партиции) и эффективно использовать BRIN-индекс.

3. **Управление жизненным циклом.** Старые данные можно удалить одной командой `DROP TABLE user_logs_y2026m01` без дорогостоящего `DELETE` + `VACUUM`. Партиции можно отсоединять (`DETACH`) и архивировать отдельно.

4. **Параллелизм.** `VACUUM` и `ANALYZE` работают независимо для каждой партиции, не блокируя запись в текущую.

### Почему помесячно, а не по дням / кварталам?

- **По дням** — слишком много партиций (365/год), каждая привносит overhead при планировании запросов.
- **По кварталам** — партиции слишком крупные, partition pruning менее эффективен при запросах за конкретный день.
- **По месяцам** — оптимальный баланс: 12 партиций/год, каждая покрывает типичный отчётный период.

### Default-партиция

Добавлена `user_logs_default` для защиты от ошибок — записи с датой вне покрытых диапазонов не потеряются, а попадут в default, сигнализируя о необходимости создать новую партицию.

## Обоснование индексов (п. 1.5)

### Индексы на `user_logs`

| Индекс | Тип | Обоснование |
|--------|-----|-------------|
| `idx_user_logs_created_at_brin` | **BRIN** | Логи вставляются хронологически → BRIN идеально подходит: занимает ~100× меньше места, чем B-tree, и эффективен для диапазонных запросов по времени. |
| `idx_user_logs_user_time` | B-tree, **partial** (`user_id IS NOT NULL`) | Лента действий конкретного пользователя. Partial исключает анонимов (~30-40% записей), уменьшая размер индекса. |
| `idx_user_logs_target_object` | B-tree, **partial** (`target_object_id IS NOT NULL`) | Поиск всех логов по конкретной теме / посту. Partial исключает записи без объекта (login, logout и т.д.). |
| `idx_user_logs_status_action` | B-tree | Агрегация по типу действия и статусу — основной паттерн DAG `forum_log_aggregation`. Составной ключ `(response_status, action_type, created_at DESC)` покрывает фильтрацию и сортировку. |

### Индексы на контентных таблицах

| Индекс | Таблица | Обоснование |
|--------|---------|-------------|
| `idx_topics_board_listing` | `topics` | Листинг тем форума: `(forum_id, is_pinned DESC, last_post_at DESC)` — закреплённые сверху, потом по свежести. |
| `idx_topics_author` | `topics` | Профиль пользователя: все его темы по дате. |
| `idx_posts_topic_created` | `posts` | Чтение темы: посты по порядку, исключая удалённые (partial `WHERE deleted_at IS NULL`). |
| `idx_posts_author` | `posts` | Все посты пользователя. Partial `WHERE author_id IS NOT NULL` — анонимные посты не индексируются. |

## DAG 1: `forum_data_generation`

Генерирует синтетические данные за один календарный месяц.

```
generate_users → generate_logs → validate_generated_data → load_to_postgres
```

**Параметры** (Airflow Params):
- `year` — год (default: 2026)
- `month` — месяц (default: 10)
- `n_users` — размер пула пользователей (default: 250)

**Гарантии и бизнес-логика:**
- **Строгая хронология сессий**: для каждого активного пользователя в рамках дня вычисляется окно сессии `(login_ts, logout_ts)`. Любые авторизованные действия (`create_topic`, `create_post`, `view_topic`, `delete_topic`) выполняются строго внутри этого окна (`login_ts < action_ts < logout_ts`).
- **Связь сущностей по времени**: сообщения (`create_post`) и просмотры (`view_topic`) гарантированно происходят после создания соответствующей темы (`topic.created_at <= post.created_at`).
- ** когортный D1 retention**: часть пользователей, зарегистрированных накануне, обязательно возвращается на следующий день, формируя корректную ненулевую метрику удержания.
- Минимум 5 действий каждого типа в каждый день месяца.
- Минимум 2 ошибки `create_topic` (попытка создания без логина) в день.
- Примерно равное распределение auth/anon постов (~50/50).
- Валидация через **pandera** перед загрузкой в БД.

## DAG 2: `forum_log_aggregation`

Ежедневная агрегация логов в CSV.

```
check_data_availability → extract_raw_logs → validate_data
    → transform_aggregates → export_to_csv → alert_on_anomaly
```

**Расписание:** `@daily` (обработка за `logical_date`).

**Ручной запуск:** передать `date_from` и `date_to` (формат `YYYY-MM-DD`) через Airflow Params.

**Особенности расчёта метрик:**
- В таске `extract_raw_logs` данные извлекаются с запасом в 1 день (`date_from - 1 день`), что гарантирует корректный расчет `topics_growth_pct` и `d1_retention_pct` даже при ежедневном запуске за одни сутки (`@daily`) без дополнительных обращений к БД.
- Итоговый датасет формируется строго за целевой диапазон `[date_from, date_to]`.

**Итоговый CSV:**

| Поле | Описание |
|------|----------|
| `day` | Дата |
| `new_accounts` | Количество регистраций |
| `anon_messages_pct` | Доля анонимных сообщений (%) |
| `total_messages` | Всего сообщений за день |
| `topics_growth_pct` | Изменение числа новых тем относительно предыдущего дня (%) |
| `avg_session_duration_sec` | Средняя длительность сессии (login → logout) |
| `d1_retention_pct` | D1 retention: доля вернувшихся на следующий день после регистрации (%) |

**Алерты:** логируются предупреждения, если `anon_messages_pct > 80%`, `total_messages = 0`, сессии < 10 сек, retention < 5% и др.

## Валидация данных (п. 5)

Используется библиотека **pandera**.

### `validate_generated_data` (DAG 1)
- **Pandera DataFrameSchema**: строгая типизация, валидация enum-значений действий и кодов ответа HTTP (`100..599`).
- **Хронология сессий**: ассерты проверяют, что для каждого пользователя все действия строго заключены между `login` и `logout`.
- **Хронология тем и постов**: ассерты проверяют, что ни один пост или просмотр не датирован раньше создания темы.
- Нет логаута без логина (`logout_uids == login_uids`).
- Успешное создание темы — только залогиненными пользователями (`user_id NOT NULL`).
- Ошибочное создание темы — только анонимами (`user_id IS NULL`).
- Минимум 5 действий каждого типа в день.
- Минимум 2 ошибки `create_topic` в день.
- Баланс постов: 30–70% анонимных.

### `validate_data` (DAG 2)
- **Pandera DataFrameSchema** с автоприведением типов (`coerce=True`) для безопасной работы с `datetime64[ns, UTC]` и `datetime64[us, UTC]`.
- Отсутствие неожиданных NULL в обязательных полях (`description`, `action_type`, `created_at`).
- Проверка бизнес-правил: успешное создание темы только с указанным `user_id`.
